# 维基百科名词库导入项目需求与实施方案

> 文档用途：交由 MiniMax 或其他开发 Agent 直接实施  
> 项目：wxreader-knowledge  
> 文档版本：v1.0  
> 编写日期：2026-10-08  
> 状态：待实施

## 1. 项目背景

当前系统已经提供“名词库”页面，至少包含以下能力或展示字段：

- 名词名称；
- 名词解释/摘要；
- 标准名称；
- 来源；
- 确认状态；
- 查看详情；
- 新建名词；
- 搜索名词或解释。

现有名词主要依赖人工创建或编辑。为了快速构建覆盖面较广的中文名词知识底座，需要引入中文维基百科作为候选名词与解释来源，同时保留人工编辑内容的优先级和最终决定权。

本项目不是搭建完整的维基百科镜像，也不是将 MediaWiki 数据库原样复制进业务数据库，而是构建一条可重复执行、可中断恢复、可审计的离线数据管道，从中文维基百科公开数据 dump 中提取适合本系统的结构化名词数据。

## 2. 项目目标

### 2.1 核心目标

1. 支持从 Wikimedia 官方中文维基百科 dump 导入名词候选数据。
2. 提取词条标题、标准名称、重定向别名、首段摘要、来源地址和版本信息。
3. 不覆盖人工创建或人工编辑的内容。
4. 导入数据默认进入“待确认”状态，由人工确认后成为正式名词。
5. 支持全量初始化、失败续跑、重复执行和后续版本更新。
6. 对下载、解析、清洗、写库的全过程提供进度、日志、统计和错误记录。
7. 在页面中正确展示来源、许可证和原始词条链接。

### 2.2 非目标

第一期不实现：

- 维基百科全部历史修订版本导入；
- 图片、音频、视频等媒体资源下载；
- 讨论页、用户页、模板页、分类页正文导入；
- 完整 MediaWiki 模板渲染引擎；
- 将所有维基正文直接生成向量；
- 实时跟踪每一次维基百科编辑；
- 自动把所有导入数据标记为“已确认”；
- 替换系统已有的 AI 解释能力；
- 将维基百科作为唯一事实来源。

## 4. 数据源与容量规划

### 4.1 官方数据源

使用 Wikimedia 官方中文维基百科 dump：

```text
https://dumps.wikimedia.org/zhwiki/latest/
```

生产导入首选：

```text
zhwiki-latest-pages-articles-multistream.xml.bz2
zhwiki-latest-pages-articles-multistream-index.txt.bz2
zhwiki-latest-md5sums.txt
```

允许使用分片版 `pages-articles-multistream*.xml-*.bz2`，并行处理时优先使用官方分片，不要自行按字节任意切割单一 XML 文件。

仅构建标题候选库时可使用：

```text
zhwiki-latest-all-titles-in-ns0.gz
```

禁止使用 `pages-meta-history`，因为其包含所有历史版本，数据量和处理成本远超本项目需求。

### 4.2 容量基线

2026-10-01 中文维基 dump 参考值：

- 主命名空间标题压缩包：约 17 MB；
- 当前正文普通压缩包：约 3.43 GB；
- 当前正文 multistream 压缩包：约 3.61 GB；
- 所有命名空间当前内容：约 4.79 GB。

生产环境建议至少预留：

- 原始下载及临时文件：15 GB；
- 清洗后的摘要数据和业务表：10 GB；
- 数据库索引与任务日志：10 GB；
- 安全余量：15 GB；
- 总可用空间建议：不低于 50 GB。

程序不能假设上述数字固定。下载前必须通过 HTTP 元信息或 dump 目录取得实际文件大小，并检查可用磁盘空间。

## 5. 业务原则

### 5.1 人工内容优先

数据优先级从高到低为：

1. 人工创建且人工维护；
2. 人工确认后又经过人工编辑的维基条目；
3. 人工确认但尚未人工编辑的维基条目；
4. 新导入、尚待确认的维基候选条目；
5. AI 临时生成、尚未保存的解释。

任何定时更新都不得覆盖第 1、2 类数据的人工字段。

### 5.2 来源可追溯

每条维基数据必须能够追溯到：

- 维基页面 ID；
- revision ID；
- 原始标题；
- 原始页面 URL；
- dump 日期或版本；
- 导入任务 ID；
- 导入时间；
- 许可证标识。

### 5.3 幂等与可恢复

- 同一个 dump 重复导入不得制造重复名词或重复别名。
- 任务中断后可以从检查点继续。
- 单条坏数据不能导致整个任务失败。
- 全量更新应写入临时批次或 staging 区，完成校验后再发布。

## 6. 用户角色与使用场景

### 6.1 管理员

- 查看可用 dump 版本；
- 创建导入任务；
- 查看下载和解析进度；
- 暂停、恢复或取消任务；
- 查看错误样例和导入统计；
- 发布成功批次；
- 清理失败任务产生的临时文件；
- 对候选名词进行批量确认或忽略。

### 6.2 普通用户

- 搜索已发布、符合可见性规则的名词；
- 查看名词解释和来源；
- 打开原始维基百科页面；
- 区分“待确认”和“已确认”内容。

### 6.3 系统任务

- 下载并校验 dump；
- 解析、清洗、写入 staging；
- 生成导入报告；
- 根据策略发布数据；
- 以后按月检查新 dump，但第一期不要求自动调度。

## 7. 功能需求

### 7.1 导入配置

管理员创建导入任务时需支持：

- 数据源 URL，默认官方 `zhwiki/latest`；
- dump 日期/版本；
- 导入模式：`titles_only`、`summary`、`full_text`；
- 是否处理重定向，默认是；
- 是否过滤消歧义页，默认是；
- 是否过滤列表型页面，默认是；
- 是否自动发布，默认否；
- 最大处理条数，测试环境可设置；
- 批量写入大小，默认 500，可配置；
- 并发数，默认 1 或安全的小值；
- 失败重试次数，默认 3；
- 临时目录。

一期默认只开放 `summary` 模式，其他模式保留程序能力或配置入口即可。

### 7.2 下载

1. 支持 HTTP 断点续传。
2. 临时文件使用 `.part` 后缀，完成后原子重命名。
3. 下载前检查目标目录可用空间。
4. 记录 URL、文件名、预期大小、已下载大小、开始时间、更新时间。
5. 下载完成后使用官方 `md5sums.txt` 校验 MD5。
6. 校验失败时禁止进入解析阶段，并保留明确错误信息。
7. 重试不得从零开始重复下载已完成部分，除非服务器不支持 Range。
8. 请求设置明确的 User-Agent，包含应用名称及管理员联系信息配置。

### 7.3 XML 流式解析

1. 必须采用流式/SAX/迭代解析，不允许把完整 XML 读入内存。
2. 只处理主命名空间 `ns = 0`。
3. 每个页面至少解析：
   - `title`；
   - page `id`；
   - redirect target；
   - revision `id`；
   - revision timestamp；
   - revision text。
4. 页面处理完立即释放 XML 节点和正文字符串引用。
5. 解析器必须兼容 XML namespace。
6. 遇到单页格式异常时写入错误表并继续。
7. 每处理固定数量页面更新一次检查点和统计，建议每 500～1000 条。
8. 不得依赖把 bz2 全量解压成 XML 后再解析；应尽量边解压边读取。

### 7.4 Wikitext 清洗

目标是得到适合列表展示和搜索的纯文本摘要，不要求完整还原浏览器渲染结果。

最低处理规则：

1. 删除注释、`<ref>`、参考文献列表和不可见标签。
2. 删除或安全展开常见信息框、导航框和维护模板。
3. 将内部链接 `[[目标|显示文字]]` 转换为“显示文字”。
4. 将 `[[目标]]` 转换为“目标”。
5. 删除文件和图片链接，如 `[[File:...]]`、`[[文件:...]]`。
6. 外部链接保留可见文本，不保留裸追踪参数。
7. 删除分类标记、语言链接和目录指令。
8. 处理 HTML 实体。
9. 合并多余空白和连续空行。
10. 首段摘要遇到第一个有效章节标题前结束。
11. 跳过空段、纯模板段和消歧义提示模板。
12. 摘要建议限制在 300～1000 个 Unicode 字符；默认 600 字符，在句号、问号、叹号等自然边界截断。
13. 不得用脆弱的单个正则表达式解析全部嵌套模板；选择成熟解析库，或实现具备嵌套深度处理的有限状态解析。

清洗后需要保存原始文本的内容哈希，但一期不建议把全部原始 Wikitext 写进主业务表。

### 7.5 标题规范化

1. Unicode 使用项目现有规范；若无规范，采用 NFC。
2. 去除首尾空白，将下划线转换为空格。
3. 保留原始中文标题，不得强制将繁体永久转换为简体。
4. 可生成简体/繁体搜索辅助键，但必须与展示标题分离。
5. 英文字母大小写规则不要自行发明，优先遵循 MediaWiki 标题行为。
6. 标准名称为重定向最终目标标题；非重定向页标准名称为自身标题。
7. 必须检测重定向环和过长重定向链；最大跳转深度建议 10。
8. 标题唯一键不得只依赖简繁转换后的文本，以免错误合并不同词条。

### 7.6 重定向与别名

- 重定向页不作为独立解释正文发布；
- 将重定向标题保存为目标词条别名；
- 如果目标页面尚未解析，先写入待解析关系，批次末统一解析；
- 目标不存在时标记为 `broken_redirect`；
- 重定向环标记为 `redirect_loop`；
- 别名应能参与搜索；
- 同一别名指向多个标准词条时不得自动合并，写入冲突记录。

### 7.7 页面过滤

默认过滤或单独标记：

- 消歧义页；
- 明显列表页，例如标题以“列表”“名单”“年表”等结尾的页面；
- 软重定向；
- 空页面；
- 只有模板、没有有效正文的页面；
- 明显维护页；
- 内容清洗后不足合理阈值的页面。

过滤必须记录原因和数量，不能静默丢弃。对于规则不确定的页面，优先标记为待确认，而不是永久删除。

### 7.8 数据写入与冲突策略

建议使用 staging + publish 两阶段：

1. 每个任务写入独立批次。
2. staging 中完成规范化、去重、重定向解析和质量检查。
3. 批次校验通过后执行发布事务或可恢复的分批发布。
4. 发布使用稳定外部键，例如 `(source, external_page_id)`。
5. 同一 revision 重复处理应直接跳过。
6. 新 revision 与现有记录相同内容哈希时只更新同步元数据。
7. 人工字段与来源字段分离，避免更新时覆盖人工内容。

冲突处理：

| 情况 | 行为 |
|---|---|
| 不存在同名记录 | 创建待确认维基候选 |
| 存在相同 page ID | 按 revision 和内容哈希更新来源快照 |
| 同名记录为人工创建 | 不覆盖；建立候选关联并写冲突记录 |
| 维基记录已人工编辑 | 更新来源快照，不覆盖人工展示内容 |
| 同名但 page ID 不同 | 不自动合并，进入冲突队列 |
| 新 dump 中页面删除/消失 | 标记来源失效，不物理删除人工确认数据 |

### 7.9 人工审核

现有名词列表需支持：

- 按来源筛选：人工、维基百科、其他；
- 按状态筛选：待确认、已确认、已忽略、存在冲突、来源失效；
- 查看维基原始页面；
- 对比“当前展示内容”和“最新维基摘要”；
- 单条确认、忽略；
- 批量确认、忽略；
- 人工编辑后自动记录 `manually_edited = true` 或等价状态；
- 展示 dump 日期和最近同步时间。

如果本期范围不包含完整审核 UI，至少实现后端状态、单条确认以及现有页面中的来源链接；批量操作可以列为第二阶段。

### 7.10 搜索

搜索范围至少包括：

- 展示名称；
- 标准名称；
- 重定向别名；
- 摘要。

要求：

- 标准名称精确匹配优先；
- 别名精确匹配其次；
- 标题前缀匹配再次；
- 摘要全文匹配最后；
- 待确认数据是否对普通用户可见应使用现有产品规则；如果没有现有规则，默认仅管理员可见；
- 不得为了本项目擅自引入新的大型搜索基础设施。优先复用当前数据库全文搜索或项目现有搜索引擎。

### 7.11 任务管理

任务状态建议：

```text
pending
downloading
verifying
parsing
resolving_redirects
validating
ready_to_publish
publishing
completed
paused
cancelled
failed
```

状态迁移必须经过服务层统一控制，不允许任意更新。

任务详情需提供：

- 当前阶段；
- 总字节数、已下载字节数；
- 扫描页数；
- 有效词条数；
- 重定向数；
- 过滤数；
- 新增、更新、跳过、冲突、失败数量；
- 当前处理文件或分片；
- 处理速率；
- 开始时间、更新时间、预计剩余时间；
- 最近错误；
- 日志或报告下载入口。

进度更新需要节流，避免每处理一条就写数据库。

## 8. 数据模型建议

必须先复用和扩展现有名词表。以下为逻辑模型，不要求表名完全一致。

### 8.1 名词主表扩展

如果现有表无法表达，增加：

```text
source_type              manual | wikipedia | other
external_page_id         维基 page ID，可空
source_revision_id       revision ID，可空
source_url               原文 URL
source_dump_version      dump 日期或版本
source_updated_at        原修订时间
source_synced_at         本地同步时间
license_code             CC-BY-SA-4.0
review_status            pending | confirmed | ignored | conflict | source_missing
manually_edited          boolean
source_content_hash      清洗前或规范化后的稳定哈希
published_batch_id       导入批次 ID
```

建议约束：

- `(source_type, external_page_id)` 条件唯一；
- `source_revision_id` 建索引；
- `review_status` 建索引；
- `standard_name` 或现有规范化字段建搜索索引；
- URL 和长文本不建立普通 B-tree 索引。

## 9. 服务与模块划分

遵循现有项目结构，逻辑上至少拆分：

```text
wikipedia-dump-client     获取版本、下载、续传、校验
wikipedia-stream-parser   解压和流式 XML 解析
wikitext-cleaner          Wikitext 到纯文本/摘要
title-normalizer          标题和搜索键规范化
redirect-resolver         重定向关系解析
glossary-import-service   批量写入 staging、校验、发布
import-job-runner         状态机、检查点、暂停恢复
import-report-service     统计与报告
```

模块之间使用明确的数据结构，不把数据库操作混入底层 XML parser。

长任务不得运行在普通 HTTP 请求生命周期内。应使用项目已有 worker/queue；若项目没有队列，一期至少实现独立 CLI 命令，并让 API 只创建任务，不在请求内执行数小时。

## 10. API/CLI 需求

路由应遵循项目现有风格。逻辑能力如下：

```text
POST   /api/admin/glossary-imports
GET    /api/admin/glossary-imports
GET    /api/admin/glossary-imports/:id
POST   /api/admin/glossary-imports/:id/pause
POST   /api/admin/glossary-imports/:id/resume
POST   /api/admin/glossary-imports/:id/cancel
POST   /api/admin/glossary-imports/:id/publish
GET    /api/admin/glossary-imports/:id/errors
GET    /api/admin/glossary-imports/:id/report
```

最低 CLI 能力：

```text
glossary wikipedia inspect --source <url>
glossary wikipedia import --mode summary --dump-version <date>
glossary wikipedia resume --job <id>
glossary wikipedia validate --job <id>
glossary wikipedia publish --job <id>
glossary wikipedia cleanup --job <id>
```

实际命令需集成到现有 package scripts、框架命令或二进制入口。所有命令提供 `--help`，支持测试用 `--limit`，输出机器可读的结束摘要。

## 11. 安全要求

1. 导入管理 API 仅管理员可访问。
2. 数据源默认只允许 Wikimedia 官方 HTTPS 域名，防止 SSRF。
3. 若允许自定义 URL，必须做域名白名单、DNS/IP 检查和重定向校验。
4. XML 解析器必须禁用外部实体和 DTD，防止 XXE。
5. 解压过程设置文件大小、压缩比或最大处理量保护，防止压缩炸弹。
6. 清洗后的 HTML 如有任何保留，必须经过项目统一 XSS sanitizer；更推荐只保存纯文本。
7. 下载文件名不得直接用于任意路径拼接，避免路径穿越。
8. 管理操作写入审计日志。
9. 错误日志不得包含密钥、Cookie、完整连接串等敏感信息。
10. 取消任务应安全停止在批次边界，不得留下部分发布且无状态记录的数据。

## 12. 授权与产品展示要求

维基百科文本通常按 CC BY-SA 4.0 等许可提供。产品至少应：

1. 在词条详情显示“内容来源：维基百科”。
2. “维基百科”文字可点击到具体原始词条，而不是只链接首页。
3. 显示 `CC BY-SA 4.0` 及其许可证链接。
4. 显示“内容已提取/节选/可能经过格式清理”等修改说明。
5. 保留原始页面链接，以便访问页面历史和贡献者信息。
6. 不把维基百科 Logo 当作本产品 Logo，也不暗示获得 Wikimedia 官方背书。
7. 图片不纳入一期；未来导入图片时必须逐项处理各自许可证。

建议详情页文案：

```text
本文摘要节选并整理自维基百科“{title}”词条，原文由其贡献者共同创作，
依据 CC BY-SA 4.0 许可使用。内容可能已进行格式清理或截断。
查看原文与贡献历史。
```

最终上线前应由项目负责人根据实际发布方式复核许可证合规；本文不构成法律意见。

## 13. 性能与可靠性指标

### 13.1 必须满足

- 解析过程内存占用不随已处理页面数量线性增长；
- 默认单进程解析峰值内存目标小于 1 GB；
- 数据库批量写入，不逐条提交事务；
- 同一 dump 重跑后主表数量保持稳定；
- 任意阶段失败均能看到可操作错误；
- 每 5 分钟以内持久化有效检查点；
- 中断恢复后允许少量重新处理，但不得重复发布；
- 对普通名词搜索接口的性能影响应可忽略；
- 大批量发布期间不长时间锁住名词主表。

### 13.2 建议目标

- 在常规开发机上至少达到每秒 50 个页面的解析和初步清洗能力；
- API 查询任务详情 P95 小于 500 ms；
- 名词搜索 P95 延续项目现有指标；若无现有指标，目标小于 1 秒；
- 单条解析错误率应低于 0.5%，且所有失败可统计。

## 14. 可观测性

日志使用结构化格式，至少包含：

```text
job_id
dump_version
stage
shard/file
page_id（适用时）
processed_count
elapsed_ms
error_code（适用时）
```

不得为每个成功词条输出 info 日志。成功进度按固定时间或固定数量汇总。任务完成生成报告，包含：

- 输入文件及校验和；
- 配置快照；
- 各类计数；
- 过滤原因分布；
- 冲突原因分布；
- 错误原因分布；
- 总耗时及各阶段耗时；
- 发布前后数据量变化；
- 20 条以内的错误示例；
- 最终结论：成功、部分成功或失败。

## 15. 详细实施步骤

### 阶段 0：仓库勘察与设计对齐

1. 阅读仓库说明和 Agent 指令。
2. 输出技术栈清单。
3. 定位现有名词实体、API、服务、页面和测试。
4. 画出当前名词新增、编辑、搜索的数据流。
5. 判断现有数据库是否适合 staging；如不适合，说明替代方案。
6. 检查是否已有后台任务、队列、定时任务和进度 UI。
7. 记录拟新增/修改的文件清单。
8. 先提交或展示设计差异，不直接大规模重构。

阶段产物：简短实施说明、数据迁移设计、文件变更清单。

### 阶段 1：数据模型与迁移

1. 扩展来源与审核状态字段。
2. 新增别名表、导入任务表、staging 表、错误/冲突表。
3. 添加外键、唯一约束及必要索引。
4. 为存量名词回填 `source_type`；不能识别时按人工数据处理，避免被覆盖。
5. 编写向前迁移；若项目惯例要求，编写安全回滚迁移。
6. 写数据库层测试：唯一约束、关联删除策略、枚举状态和索引查询。
7. 在有代表性的数据副本上评估迁移锁表风险。

完成条件：迁移可在空库和已有数据的库上执行，存量名词不丢失。

### 阶段 2：小样本夹具和解析器

1. 不要一开始下载完整 3.6 GB 文件。
2. 建立最小 XML 测试夹具，覆盖普通词条、重定向、繁体标题、模板、链接、ref、消歧义、空页、坏格式。
3. 实现 bz2 输入抽象，使测试可使用小文件或内存流。
4. 实现安全 XML 流式解析器并禁用外部实体。
5. 每输出一页后释放解析节点。
6. 为 page/revision ID 区分写单元测试，避免把 revision ID 当 page ID。
7. 实现解析错误隔离。

完成条件：测试夹具逐条输出稳定结构，内存不会随重复夹具数量增长。

### 阶段 3：Wikitext 清洗与摘要

1. 调研并优先选择与当前语言栈兼容、仍在维护的 Wikitext 解析库。
2. 锁定依赖版本并记录选择理由。
3. 实现链接、引用、模板、HTML 实体等清洗规则。
4. 实现首个有效段落提取。
5. 实现自然句边界截断。
6. 输出纯文本，保证前端按文本渲染不会执行 HTML/脚本。
7. 建立中文样例快照测试。
8. 对特别复杂页面允许退化为较短摘要并写质量标记。

完成条件：至少覆盖 30 个有代表性的中文 Wikitext 用例。

### 阶段 4：下载、校验与任务状态机

1. 实现官方源信息检查。
2. 实现磁盘空间预检。
3. 实现断点下载和 `.part` 原子改名。
4. 实现 MD5 文件解析与校验。
5. 实现任务状态迁移规则。
6. 实现暂停、取消信号；在安全批次边界响应。
7. 实现检查点持久化。
8. 模拟网络中断、校验失败和磁盘空间不足。

完成条件：小文件可中断续传，错误状态明确，非法状态迁移被拒绝。

### 阶段 5：Staging 写入和重定向解析

1. 将解析结果按批写入 staging。
2. 用 `(job_id, page_id)` 保证幂等。
3. 任务中记录扫描、过滤、成功和失败计数。
4. 初次解析结束后构建标题到 page ID 的映射。
5. 解析重定向链、环、缺失目标。
6. 生成别名候选。
7. 执行批次质量校验。
8. 生成导入报告预览。

完成条件：相同小样本执行两次，staging 不重复，重定向结果一致。

### 阶段 6：发布与冲突保护

1. 实现新词条创建。
2. 实现已有维基词条按 revision 更新。
3. 实现人工数据保护。
4. 实现人工编辑维基词条的双轨字段或快照机制。
5. 实现同名冲突记录。
6. 实现来源消失标记，不直接删除正式数据。
7. 分批发布，记录每批游标和结果。
8. 发布失败后可以继续，不重复插入。

完成条件：用冲突矩阵中的所有情形完成集成测试。

### 阶段 7：管理 API、CLI 与页面

1. 创建管理员任务 API。
2. 实现任务列表、详情、暂停、恢复、取消、发布。
3. 实现错误列表和报告。
4. 接入权限控制和审计。
5. 提供 CLI，以便服务器后台稳定执行。
6. 在名词列表增加来源和状态筛选。
7. 在详情页增加来源 URL、许可证和修改说明。
8. 根据项目能力实现轮询、SSE 或现有实时机制展示进度。
9. 页面处理长标题、长错误信息和无进度总量的情况。

完成条件：管理员能从小样本创建任务到发布；普通用户不能调用管理接口。

### 阶段 8：完整 dump 试跑

1. 先运行 `--limit 1000`。
2. 人工抽查不少于 50 条摘要、20 条重定向和所有错误样例。
3. 再运行单个官方分片。
4. 记录吞吐、内存、CPU、数据库增长、索引耗时。
5. 修复明显清洗与冲突问题。
6. 下载完整 dump，核对 MD5。
7. 完整解析到 staging，不自动发布。
8. 查看报告和异常分布。
9. 备份数据库或确认可恢复点。
10. 管理员确认后发布。
11. 发布后验证页面、搜索、分页和详情来源。

### 阶段 9：运维与更新

1. 文档化首次导入命令。
2. 文档化恢复、取消和清理方式。
3. 文档化磁盘空间和数据库监控。
4. 制定每月检查一次新 dump 的流程。
5. 第一阶段采用人工触发更新；稳定后再增加定时任务。
6. 新批次发布后，旧 staging 保留可配置天数再清理。
7. 清理只删除明确归属于已结束任务的临时文件，不使用宽泛路径或通配符。

## 16. 测试要求

### 16.1 单元测试

- XML namespace 和字段解析；
- 普通页与重定向页；
- Wikitext 嵌套模板；
- 中文内链和带显示文字的内链；

- 标题规范化；

- 内容哈希稳定性；
- 状态机合法/非法迁移；
- MD5 校验；
- 断点续传区间处理。

### 16.2 集成测试

- 小型 bz2 dump 到 staging；
- staging 到发布；
- 重复运行幂等；
- 人工内容不被覆盖；
- revision 更新；
- 发布中断后恢复；
- 取消任务；
- 管理权限；
- 搜索命中标准名称和别名；

- 至少 10 万页面的连续解析；

- 测量不同 batch size；
- 测量索引存在时批量 upsert 的速度；
- 测量发布期间前台搜索延迟。

### 16.4 回归测试

- 现有人工新建名词；

- 名词搜索与分页；
- AI 助手读取名词；
- 其他使用名词实体的知识图谱功能。

## 17. 验收标准

以下条件必须全部满足：

1. 可以用小样本和官方 dump 创建导入任务。
2. 下载支持断点续传并完成 MD5 校验。
3. 只导入主命名空间页面。
4. 能得到可读的中文首段摘要。
5. 重定向正确生成别名，链、环和断链有处理结果。
6. 同一 dump 重复运行不会制造重复名词。
7. 人工创建和人工编辑内容不会被覆盖。
8. 新导入数据默认为待确认。
9. 每条数据可追踪 page ID、revision ID、dump 版本和来源 URL。
10. 详情页展示来源及 CC BY-SA 4.0 说明。
11. 管理员可查看任务进度、统计和错误。
12. 普通用户无法创建、发布或取消任务。
13. 解析中断后可恢复。
14. 完整处理时内存占用基本稳定。
15. 所有新增测试通过，现有测试无新增失败。
16. 类型检查、lint 和生产构建通过。
17. 提供运维文档、配置说明和完整导入报告示例。

## 18. 推荐交付顺序

为了降低风险，按以下 PR/提交拆分：

1. 数据模型、迁移和数据访问层；
2. XML parser、Wikitext cleaner 及夹具测试；
3. 下载、校验、任务状态机和 CLI；
4. staging、重定向和验证报告；
5. 发布、幂等和冲突保护；
6. 管理 API 与权限；
7. 管理 UI、来源展示与搜索增强；
8. 完整 dump 性能修复和运维文档。

每一步都必须保持项目可构建、测试可运行。不要把所有功能堆在一个无法审查的大提交中。

## 19. MiniMax 执行指令

执行本需求时遵守以下规则：

1. 先勘察、再设计、后编码；不要假设技术栈。
2. 优先复用现有模型、组件、任务框架和编码规范。
3. 不修改与本需求无关的文件。
4. 不删除用户已有改动。
5. 所有数据库变更必须通过项目迁移机制。
6. 所有长任务必须可观察、可中断、可恢复。
7. 不允许为图省事一次性读取完整 dump。
8. 不允许默认覆盖人工内容。
9. 不允许在生产页面渲染未经清洗的 Wikitext 或 HTML。
10. 每完成一个阶段运行对应测试，并记录命令和结果。
11. 发现本文与现有架构冲突时，选择对现有系统侵入更小的实现，并在交付说明中解释。
12. 不在没有验证小样本前运行完整 dump。
13. 不在没有管理员确认和备份/恢复方案前发布完整批次。
14. 最终交付时列出新增配置、迁移、命令、已知限制和后续建议。

## 21. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Wikitext 复杂，摘要清洗不完整 | 页面出现模板残留 | 使用成熟解析库、质量标记和人工抽查 |
| dump 体量持续增长 | 磁盘不足、耗时增长 | 下载前探测大小、容量预检、分片处理 |
| 人工内容被同步覆盖 | 数据损失 | 来源字段分离、人工优先、冲突测试 |
| 重定向造成错误合并 | 词条关系错误 | page ID 稳定键、环检测、冲突队列 |
| 完整发布锁表 | 影响前台 | staging、分批 upsert、短事务 |
| 导入中断 | 大量重复工作 | 检查点、幂等键、断点续传 |
| 许可证展示遗漏 | 合规风险 | 统一来源组件、验收项、上线复核 |
| SSRF/XXE/压缩炸弹 | 安全事件 | 域名白名单、安全 XML 配置、资源上限 |
| 简繁转换误合并 | 数据错误 | 简繁只作为搜索辅助，不作为唯一键 |

## 22. 后续版本候选

完成一期并稳定运行后可考虑：

- 每月自动检测和增量更新；
- Wikimedia EventStreams 或 API 辅助更新；
- Wikidata QID 对齐，增强实体消歧；
- 使用分类信息改进领域筛选；
- 只对人工确认词条生成 embedding；
- 新旧维基摘要差异审核界面；
- 按用户阅读书籍动态拉取相关名词；
- 导入指标监控面板；
- 多语言维基来源；
- 基于 pageview 的优先级排序。
